# Cross-verification audit — 2026-09-14

Scope: the adaptive interviewer on `feat/orb-and-conversation-engine`, judged as an
interviewer, not as a build. Triggered by a candidate report: *Haris asks the
same question again — sometimes after it was answered.* Everything below was
reproduced or measured on this source; nothing is inferred from tests passing.

## A. Root cause of repeated questions

Reproduced three ways: a harness that drives the real orchestrator with realistic
*spoken* answers (`test/repetition.test.ts`), a paced live Groq round on the
unfixed code, and a phoneme/audio measurement of the production voice. Five
causes, one shared mechanism.

1. **The deterministic answer classifier called complete spoken answers "vague".**
   `lib/interview/analysis.ts` keyed "specific" on digits and a short buzzword
   list; ownership only on ~25 verbs. Six of eleven realistic spoken answers
   ("I did the whole backend part, the login and listing pages talk to my
   APIs…", the polymorphism answer with a concrete Payment interface) read as
   `vague`, and "I did the whole backend" was flagged an *overclaim*. Everything
   downstream then asked the candidate to say it again: `clarify` ("be
   specific"), `challenge` ("that's a big claim"), `probe_resume` on a claim they
   had just discussed, and `follow_up` after `follow_up` on the same ground.
   In model mode the same misreading was injected into the prompt as *"Their
   last answer read as: vague — Recommended: clarify"*.
2. **The fallback interviewer (what speaks under a Groq 429) reused three
   "be specific" lines with no memory check.** Exact repeats appeared within
   one round (`Let's pin that down…` twice, `That's still quite general…` twice).
   The free tier rate-limits often, so this path spoke frequently.
3. **The model was never told what it had already asked or established.** The
   prompt keeps a 16-entry transcript window, so from mid-round the model could
   not see the opening exchange; the Supermemory "already asked" block is
   per-instance and cached for 10 minutes, so on Vercel it rarely carried the
   current session. Live baseline, turn 3: *"how did you enforce that
   uniqueness — did you add a database constraint…"* right after the candidate
   said *"a unique check in the database so only one order can exist"*.
4. **Question memory was exact-match only.** `wasAlreadyAsked` caught a
   verbatim repeat; a rewording passed, and nothing checked a question against
   the candidate's *answers*.
5. **"Probe once, then move on" was not enforced.** Two clarifies plus follow-ups
   per thread were allowed and `switch_competency` was refused until coverage
   was reached — with cause 1 that meant up to four questions on one competency
   after full answers (live baseline: three consecutive project follow-ups).

Also found, not a repetition cause: `(no answer)` after an STT drop re-asked the
question verbatim with no acknowledgement, which a candidate who *did* speak
experiences as "it asked me again".

### What changed

- `lib/interview/analysis.ts` — recalibrated for speech: ~70 ownership verbs,
  plural-aware tech vocabulary including plain words ("backend", "bucket",
  "login"), number words, causal and example phrases, resume project names as
  examples; strong/adequate thresholds no longer need digits; overclaim only
  for sweeping claims with nothing behind them. All eleven spoken answers now
  read adequate or strong; an empty answer still reads vague.
- `lib/interview/dedupe.ts` (new) — the semantic half of interview memory:
  content terms with stemming and interviewer/candidate synonyms
  (pick/choose, built/create, fix/solve…), `isSameQuestion` for rewordings,
  `alreadyAnswered` for follow-ups whose answer is in the transcript
  (why/how questions need an explanation, "tell me more" is never "answered").
- `lib/interview/orchestrator.ts` — every model question is checked against
  asked questions (semantic) and, for probing moves, against every answer in
  the round; a hit is rejected and regenerated once with the rejection stated in
  the prompt and a *different* move forced (`alternativeMove`, new ground
  first). The fallback receives the same answers and never speaks a repeat.
- `lib/interview/brief.ts` — the model now sees *ASKED ALREADY THIS INTERVIEW*
  (last 8), *Already established on this ground* (verified quotes for the
  current competency), and *"It answered the question — do not ask for the
  same explanation again"* after a complete answer. Silence is acknowledged
  ("I didn't catch that") before the re-ask.
- `lib/interview/actions.ts` — one clarify per thread; switching is allowed once
  the candidate was probed and is still thin, or after two probes with some
  evidence; `alternativeMove` for regeneration.
- `lib/interview/fallback.ts` — every templated line goes through the same
  memory checks; larger pools; no "You mentioned Java — what was your part in
  that".
- `lib/interview/engine.ts` — an adequate answer that discusses a resume claim
  supports it (so it is not probed again).
- `hooks/useInterviewMachine.ts` — a refresh resumes the round from
  sessionStorage (history, transcript, signed state); the pending question is
  spoken again, nothing is re-asked. Leaving the room discards it.

## C. Genuinely working (verified live)

- Model-written turns with server-validated moves; invalid moves regenerated.
- Contradictions raised with the candidate's own quotes (technical and HR).
- Coding exercise seeded in code; model catches a submission that solves the
  wrong problem.
- Fallback keeps the round adaptive under a 429 (no scripted bank).
- Signed state round-trips; tampering rebuilds from the transcript.
- Readiness report and server-side scoring returned on the preview.

## D. Implemented but not (yet) exercised end to end

- Refresh-resume and auto-retry: logic in the hook, not driven in a browser here.
- History/progress trend table: compiles and renders from stored sessions; no
  multi-session browser run this audit.
- Expressions: verified by phonemes/durations, not by ear. Chatterbox (local
  studio voice) was not running, so its tag performance is documented, not measured.

## E. Remaining architectural gaps

1. **Question planning is still ad hoc per turn.** DeepInterview pre-plans a
   question set from CV + JD before the call; we generate each question live.
   A one-time plan of 2–3 targeted questions per competency (one background
   call at session start) would make questions more resume-specific and cut
   repetition further. Not done: costs one extra call per session.
2. **Transcript window** stays at 2 + 14 entries; the asked/known blocks cover
   the gap, but a long HR round still loses middle context for nuance.
3. **STT drops read as silence.** An answer the recogniser lost becomes
   `(no answer)`; the interviewer now says it didn't catch that, but cannot
   tell "silent" from "unheard". A confidence signal from STT would help.
4. **No LLM-driven candidate simulation.** The harness uses scripted candidates;
   Interviewer's approach (LLM candidates graded by a strict judge) would catch
   prompt regressions the scripts cannot.
5. **Per-instance memory on Vercel.** In-process "asked this process" and the
   10-minute recall cache don't survive across lambdas; the signed state now
   carries what matters within a session, but cross-session recall still
   depends on Supermemory's ~20 s indexing delay.
6. **Quality of the model's follow-ups is bounded by the model.** The checks
   reject repeats; they cannot make a shallow question deep.
7. **The memory check is lexical.** It catches literal and near-literal re-asks
   (the reported failure) but not a paraphrase with different vocabulary
   ("broke the night before the fest" vs "broke before a release"). Closing
   that needs a judged check — one small background call, or embeddings.

## F. Recommended next upgrades

- Session-start question plan (see E1), executed as candidates for the model
  to adapt, not read verbatim.
- An LLM-candidate evaluation harness with pass/fail rules (no repeats, no
  hints during coding, silence nudged once, vague probed once).
- Persist the resume record in IndexedDB keyed by session id so a *new tab*
  can also resume.
- Listen to the expression clips (`node scripts/verify-expressions.mjs ./out`)
  and prune by ear; measure Chatterbox with the same script when it is running.

- `npm run check` (typecheck + build + tests): green — 2,205 tests in 65 files.
- New: `test/repetition.test.ts` (exact/reworded/already-answered repeats,
  deeper follow-up allowed, one-clarify rule, resume claim supported, retry and

### Live Groq runs (paced 12 s between turns, free tier)

Baseline (before the fixes), technical: 7 model turns; turn 3 re-asked how
uniqueness was enforced immediately after the candidate said "a unique check in
the database"; three consecutive follow-ups on the project before coding.

After the fixes, technical (12 turns, 1 fallback under a 429): no exact or
reworded repeat; one follow-up on the project, then coding; the model caught a
submission that solved the wrong problem; difficulty stepped up on
problem-solving; the memory check rejected one repeated question live and
regenerated it with a different move. One partial re-ask slipped through (turn
8: "which version of Spring Boot… and why you chose it" after the choice had
been explained on turn 1) because the already-answered check looked at only
the last six answers — it now reads the whole round.

After the engine fixes, HR (14 turns, 2 fallbacks): communication →
adaptability → self-awareness → motivation → teamwork → pressure, six of seven
required competencies assessed (progress 1.0), never more than three
consecutive turns on one competency, reactions in use ("Interesting, Ravi.",
"Hmm, okay.", "I see."). Before the engine fixes the same script sat on
adaptability for eleven turns and raised a bogus contradiction. Remaining
weakness, visible on turn 12: a canned fallback probe restated, in different
words, a story the candidate had just told; the lexical check cannot bridge
that vocabulary gap (see E).
